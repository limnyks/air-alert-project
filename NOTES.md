## 1. Task & rules

### Organizers' requirements (as given by the user)
- Build a mini pet project in Python: time series analysis and forecasting of air raid alerts in Ukraine.
- Must be a genuine model that reflects the true state of affairs and, based on that, predicts an alert and its duration.
- Use the most recent data available and evaluate on the latest period.
- No data leakage: nothing the model is trained on or uses as input may come from after the time the forecast is made.
- Optional: text data (news, official statements, public Telegram channels), same rule: only content published before the forecast time.
- Deliverables: a GitHub repo with working Python code, the conversation log, and a ~100-word reflection.
- They evaluate the process: how the user iterates, catches mistakes and guides the architecture.

### Working rules (user's rules for the assistant)
1. Explain the plan before writing code, wait for the user's decision, and write code only after approval.
2. Small steps. After each step the user runs the code and shows the output.
3. Do not invent datasets, APIs, columns or results. If unsure something exists, say so and give a link to check.
4. Every claim about the data must come from output we actually saw.
5. The user makes the key decisions. The assistant gives options with pros and cons.
6. If more info is needed, ask. Details about the task are known only if the user states them.
7. (added 2026-10-11) Every option lists its external dependencies and what happens if each fails (after mistake M4).
8. (added 2026-10-11) No bare risk lists: for each risk, write a solution right away, critique it three times, and present only the finalized result.

## 5. Leakage checklist
- [ ] Censoring: an alert ongoing at time t has no known end time; never use its real end time as input.
- [ ] Rolling/lag features use only data strictly before t.
- [ ] Other regions' alerts are used only if they started before t.
- [ ] Timezones & DST handled consistently (Kyiv time vs UTC).
- [ ] Text data uses the original publication time, not edit or scrape time.
- [ ] Time-ordered split only: train on the past, test on the latest period. No random shuffling.
- [ ] Hyperparameters tuned on a validation period, never on the test period.
- [ ] Purge: no training label window (up to +24h) may reach into the validation/test period.
- [ ] Lag guard in code: any feature lag ≤ 0 raises an error.
- [ ] Automated leakage test: λ(t) computed from data cut at t equals λ(t) from full data and from data with fake future alerts; deliberately leaky features must make the test fail.
- [ ] Trend in μ(t) is causal (computed from the past only; no two-sided smoothing).
- [ ] Weather (if used): only values known at t (observations or forecasts issued before t), never actual future weather.
- [ ] Known limitation, not fixable in code: the source data may contain later corrections (retroactive edits).

## 11. Known limitations (no full solution)
1. Adversary decisions (start of a mass attack) cannot be predicted from alert history; Hawkes can only react once a wave starts.
2. Retroactive corrections in source data (leakage hidden in the history itself); documented, not fixable.
3. Regions without data (Luhansk, Crimea, occupied areas) → "no data" on the map (D13).
4. Freshness depends on dataset maintainers → backup source only reduces the risk.
5. Predictability ceiling: careful projects all report modest gains; our goal is honest measurement, not impressive numbers.
6. Separating self-excitation from a slowly changing rate is mathematically hard; only the out-of-sample test (M1 vs M0) decides.
7. Telegram (Q13): unsolved until Step 4 facts are in.
8. **Telegram AI/ML terms (2026-10-11):** using Telegram data to train/validate/benchmark ML models is prohibited; our long history (Vadimkin files) was built from Telegram → grey zone, documented in README. **User decision D25: text (Telegram or news) stays in the plan; Telegram risk accepted knowingly if Telegram is chosen later.**
9. **Train/test label consistency (D23) cannot be checked directly:** the official file (to 2026-09-07) and the alerts.in.ua snapshot (from 2026-09-11) do not overlap in time, except alerts that started before the window; the official file has no alert-type column (H9).

## 12. Evaluation protocol — FROZEN 2026-10-11 (D31; change only via a new decision entry)

_Frozen text committed in `d369009`._

### 12.1 Units, labels, periods
- **Units:** the 104 modeled units in `logs/step10b_raion_checks.csv` (`excluded == False`): 103 raions + Kyiv City. The 15 excluded raions are shown as "near-permanent alert (> 80 % of time)" and reported descriptively only.
- **Labels:** `data/processed/raion_episodes.csv` — unit under alert = oblast-wide alert OR an alert for the raion; alerts.in.ua air_raid only; gaps ≤ 2 min joined; alerts running at the snapshot censored.
- **Training data:** official file from each unit's `train_from` to 2026-09-07 05:28 UTC.
- **Validation (all model choices):** 4 folds × 14 days, 2026-05-18 → 2026-07-13; refit before each fold on data up to the fold start minus a 24 h purge.
- **Pre-reform test (secondary):** forecast origins 2026-07-13 00:00 → 2026-09-06 05:00 UTC (labels to the official end); model fitted on data up to 2026-07-12 00:00 (24 h purge), parameters fixed during the block.
- **Gap:** 2026-09-07 05:28 → 2026-09-11 08:22 — no data; never imputed.
- **Adaptation week:** 2026-09-11 08:22 → 2026-09-18 08:22 (alerts.in.ua): one shared post-reform level multiplier + per-unit multipliers shrunk toward it; warm-up history for inputs. Not used for model choices.
- **Post-reform test (PRIMARY, "latest period"):** forecast origins 2026-09-18 09:00 → 2026-10-10 08:00 UTC on full hours (22 days; labels to the snapshot 2026-10-11 08:22). Model fitted on all training data, then adapted. Touched once; run date and git commit recorded in NOTES.
- **Prospective test (extension):** after freezing the model, further alerts.in.ua snapshots add only days after 2026-10-11 08:22; reported separately; the model is not changed.

### 12.2 Forecast targets (unit u, origin t on every full UTC hour)
1. **Map target (primary):** P(X_u(t+h) = 1 | history before t), h = 1 … 24 h; X_u = instantaneous alert state.
2. **Secondary map target:** P(any alert of u during (t+h−1 h, t+h]), h = 1 … 24 h.
3. **Next start:** distribution of the next start time in hourly bins k = 1 … 24 and "> 24 h", at origins where u is off.
4. **Duration:** (a) at each alert start: distribution of its duration; (b) at origins where u is on with elapsed e: distribution of the remaining duration.
- Inputs: only events that started before t; running alerts have unknown ends; history lookback ≤ 72 h.

### 12.3 Metrics and claims
- **Primary metric** (amended by D38): skill = 1 − macroBrier(model) / macroBrier(best baseline), Brier averaged over h = 1 … 24 and per unit, then over units (each unit counts equally), one ratio; micro skill and per-horizon skill reported alongside; vs the **best baseline** = the baseline with the best validation Brier score (chosen before any test).
- Also: log loss; micro averages (report only); reliability table (10 bins) + ECE, "confident but wrong" share (≥ 0.8 or ≤ 0.2 and wrong), PR-AUC (report only).
- Next start: log score of the binned distribution; Brier for P(start within 1 / 3 / 6 h).
- Duration: censoring-aware log score; CRPS; pinball loss 10 / 50 / 90 %; coverage of the 80 % interval.
- Point-process fit: time-rescaling test (rescaled inter-start times ~ Exp(1), KS statistic) per unit, on training and test.
- **Uncertainty:** day-block bootstrap (resample whole UTC days, 2,000 replicates), 95 % intervals for every metric and every model-minus-baseline difference.
- **Claim rule:** "X beats Y" only if the 95 % interval of the macro score difference excludes 0. Per-unit results reported without claims.
- **Map threshold** (if red/gray): 0.5 on calibrated probabilities; not tuned.
- **Report only:** scores of the frozen model on the adaptation week (sanity check, never used to change choices).
- **Reporting versions:** all 104 units, and controlled-only units once the official occupied list is available (D30).

### 12.4 Baselines
- B1 climatology: per unit, share of time under alert by hour-of-week over the last 8 weeks before the data cut.
- B2 calibrated persistence: P(on at t+h | state at t), per unit and h, from training data.
- B3 7-day rolling share of time under alert before t.
- Durations: Kaplan–Meier per unit (training). Next start: empirical off-duration distribution per unit (training).
- In the post-reform test all baselines get the same adaptation multipliers as the models.

### 12.5 Model ladder (each step must beat the previous by the claim rule on validation; stop climbing when it does not)
- M0 inhomogeneous Poisson starts (daily/weekly Fourier terms + causal slowly varying trend) + parametric survival durations; outputs by Monte Carlo simulation (joint across units → per-oblast summaries).
- M1 + dependence on recent own alerts (Hawkes, exponential kernel; or a Cox hidden-intensity alternative — D41). M2 + cross-unit excitation by rings of neighbouring raions (adjacency from HDX `ukr_adminlines` left/right pcodes; fallback: HDX polygons). M3 + regime adaptation (one mechanism: recency weighting or window). M4 + text (D25). ML challenger: gradient boosting per horizon on the same inputs (D14).

### 12.6 Model selection
- All hyperparameters and ladder decisions on the 4 validation folds only; criterion: macro log loss of the map target.

### 12.7 Leakage tests (must pass before any test run)
- Inputs and λ(t) identical when computed from full data, data cut at t, and data with fake alerts added after t; deliberately leaky inputs must make the test fail; lag guard (lag ≤ 0 → error); trend in μ(t) from the past only.

### 12.8 Sensitivity analyses (report only)
- Gap rule 0 / 2 / 5 min; raion state with vs without hromada/city alerts; with vs without adaptation; censored ends as interval-censored vs excluded; all units vs controlled-only.

### 12.9 Known limits
- Primary test is 22 days (origins 2026-09-18 → 2026-10-10; "23" was a miscount, M5) → wide intervals; pre-reform test and validation reported as secondary evidence.
- Aggregate test-period statistics were seen in Steps 8b and 10b (shares, episode rates) → documented; no further use before the single run.
- Training labels pre-reform from the official file, test labels post-reform from alerts.in.ua; consistency supported only indirectly (Step 8b Check C).
- 61 units have only ~10 months of training history (after their switch).
- Occupied status unresolved at freeze time (D30).

### 12.10 Wording rules for results (D38)
- Always give the estimate **with its 95 % interval** and the test length (post-reform: 22 days of forecast origins; pre-reform: 51 days after the outage mask).
- If the interval includes 0: write "**no evidence of a difference**", never "no difference" or "the model is as good as".
- Write "**beats the baseline**" only when the claim rule holds (interval excludes 0) for the primary skill.
- Pre-reform test and validation results are **supporting evidence**, not proof for the post-reform period.
- Report the day-block interval; if the week-block interval changes the conclusion, report the more cautious one.
- Per-unit results are descriptive; no per-unit claims.
